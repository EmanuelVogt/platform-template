## Contexto

A entrada `identity/single-tenant` `3.0.0` troca os defaults de cookie por nomes neutros —
`__Host-app_session`, `__Host-app_device` e `app_csrf` — e o nome do cookie de CSRF, que era
literal em `api/guards/cookie.ts`, passa a sair da configuração (`CSRF_COOKIE_NAME`). Do outro
lado da costura, `configureClient({ csrfCookieName })` lê o mesmo nome no SPA.

Na mesma versão, `COOKIE_SAMESITE=none` deixa de ser aceito quando a API não está no host de
`WEB_ORIGIN`: o cookie de CSRF é host-only (`setCsrfCookie` não define `domain`), então o SPA
nunca conseguiria lê-lo e toda mutação autenticada levaria 403.

## Impacto

O nome do cookie é a chave da sessão no browser. Subir a `3.0.0` sem fixar os nomes antigos
**invalida toda sessão viva**: cada usuário logado é deslogado no deploy. Um filho que já
renomeava o cookie de sessão por env não é atingido nesse ponto, mas o cookie de CSRF era um
literal — ele muda para `app_csrf` em qualquer filho que não declare `CSRF_COOKIE_NAME`.

Um filho com `COOKIE_SAMESITE=none` e a API em outro host (o layout default do `copier.yml`:
front em `<app_domain>`, API em `api.<app_domain>`) **não sobe** até corrigir a topologia ou
voltar para `lax` — o que já estava quebrado em runtime passa a cair no boot.

## Passos

1. Sem deslogar ninguém: declare no ambiente da API `COOKIE_NAME=__Host-rit_session`,
   `DEVICE_COOKIE_NAME=__Host-rit_device` e `CSRF_COOKIE_NAME=rit_csrf` (os valores da `2.x`).
2. Assumindo o rename: não declare nada e comunique o logout único; no SPA, passe
   `configureClient({ csrfCookieName })` só se o nome não for `app_csrf`.
3. Com `COOKIE_SAMESITE=none`: declare `API_ORIGIN` com o mesmo host de `WEB_ORIGIN` (API sob
   proxy reverso no host do front) ou volte para `COOKIE_SAMESITE=lax`.
