## Contexto

O teste "handshake de banco por worker" (RUN-02, `db.int-spec.ts`) prova que cada worker do
tier de integração conecta no clone Postgres que o harness reservou para ele
(`test_w<índice>`). Duas das suas asserções comparavam o nome do banco realmente conectado
contra `` test_w${process.env.VITEST_POOL_ID} `` — mas `VITEST_POOL_ID` não é a fonte de
verdade do índice: como o próprio `worker-db.ts` documenta, o Vitest reconstrói a free-list
desse id a cada fronteira de `sequence.groupOrder` sem sincronizar com os workers vivos, e por
isso dois processos podem enxergar o mesmo pool id enquanto reivindicam clones diferentes via
`claimWorkerDatabaseIndex` (lock-file, atômico) — é essa função, não `VITEST_POOL_ID`, que
`testDatabaseUrl()`/`createTestPool()` realmente usam para montar `DATABASE_URL`. O teste
comparava contra a segunda fonte (o pool id bruto, uma heurística), não contra a primeira —
visto na CI de release da `v4.0.1` (`pnpm test:coverage`): `AssertionError: expected 'test_w4'
to be 'test_w3'` nas duas asserções, vermelho em uma execução, verde no rerun sem mudança de
código. Flake pura de teste: a conexão real sempre foi para o clone certo (a aplicação nunca lê
`VITEST_POOL_ID`); só a prova comparava contra a fonte errada.

A correção troca as duas expectativas para chamar `claimWorkerDatabaseIndex()` — memoizada por
processo, então a segunda chamada, feita depois de `createTestPool()` já ter reivindicado o
slot em `beforeAll`, devolve o mesmo índice sem nova disputa de lock — em vez de ler
`process.env.VITEST_POOL_ID`. Nenhum código de produção nem de harness muda:
`worker-db.ts`/`db.ts`/`global-setup.ts` já usavam a fonte certa; só a prova comparava contra a
errada.

## Impacto

Todo filho nascido em, ou atualizado para, qualquer versão do template entre `v2.0.0` (quando o
tier de integração por worker chegou) e `v4.0.1` (a HEAD atual, ainda não corrigida) pode ver
`pnpm test:int`/`test:e2e`/`test:coverage`/`test:db` vermelho neste teste, ocasionalmente —
falso negativo puro, mais provável em runs com `maxWorkers` alto ou em execuções mescladas
(`test:coverage`, que roda vários projetos Vitest na mesma free-list de pool ids). Não há
exposição de segurança nem mudança de comportamento: cada worker sempre conectou no seu próprio
clone; só a prova ficou instável.

## Passos

1. `copier update` para >= v4.0.2 (quando publicado) — republica o arquivo corrigido.
2. Se preferir corrigir no lugar sem atualizar: em
   `apps/api/src/shared/test/int/db.int-spec.ts`, troque as duas leituras de
   `process.env.VITEST_POOL_ID` por `claimWorkerDatabaseIndex(inject("postgresUri"),
   workerDatabaseCount())`, importado de `./worker-db`.
3. Confirme rodando o spec repetidas vezes com `maxWorkers` alto (`pnpm test:int -- db.int-spec`
   em loop, ou `--repeat`) — a asserção do nome do banco para de divergir do pool id.
