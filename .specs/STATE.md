# Project State — platform-template

## Decisions

Active project-level decisions. Every design must conform or supersede explicitly.

| ID | Status | Decision |
| --- | --- | --- |
| AD-001 | active | **Product slot files.** Contract-facing closed sets (permission catalogs, access profiles, upload profiles) are extended through *static slot files* the platform ships empty and the product fills with additive one-liners: `shared/kernel/access/product-permission-catalogs.ts` (precedent), `shared/kernel/access/product-access-profiles.ts`, `shared/kernel/upload/product-upload-profiles.ts`. They are static because the Zod contract (`z.enum`) is evaluated at import time and must reach `openapi.json` → Kubb → web with literal types. Slot files are the only platform files a product edits, alongside the composition root (`app.module.ts`, `db/schema.ts`, `product-routes.tsx`); the platform never adds content to them after creation, so `copier update` 3-way merge stays clean. Behaviour that is only needed at boot (notification template sources, audit registrations) uses **runtime registries** the product fills from its own module (`OnModuleInit`), never a slot file. |
| AD-002 | active | **`professional` stays a base-set access profile in v0.2** (`master`, `admin`, `professional`). The identity professional slice (scope/commitments ports, directory + assignment facades, five satellite tables in baseline 0000, `areaIds/serviceIds/schedulingAreaIds` in the user contract) is far larger than the profile literal; extracting it is a v0.3-size change with its own migration story. The profile registry (AD-001) makes that extraction a deletion later. Pending user confirmation — see spec Assumptions. |
| AD-003 | active | **`attendsGuests` → `servesClients`** (column `serves_clients`). Neutral across service businesses; keeps the verb-phrase boolean style already used by the field. `isServiceProvider` rejected: `service` is product vocabulary in the coverage sweep. |
| AD-004 | active | **Access profile persistence stays a DB enum** (`identity.access_profile`); a product adds a value with `ALTER TYPE identity.access_profile ADD VALUE IF NOT EXISTS '<key>'` in its own migration. Trade-off table in design.md. Caveat documented for products: a value added inside a migration transaction cannot be used by DML in the same migration batch (Postgres ≥ 12). |
| AD-005 | active | **Platform migrations after the baseline exist.** They keep `NNNN_<module>_<slug>` numbering continuing from 0004 and a `when` chosen at authoring time. Products are told to number their migrations from `1000_` (idx collisions are tolerated by drizzle, order = journal position) and, after `copier update`, to bump the `when` of incoming platform entries above their last applied migration when `db:check:journal` fails (a not-yet-applied entry may be re-stamped; an entry born in the past is silently skipped forever). |
| AD-006 | active | **Version truth = git tag + `docs/dev/template-changelog.md`.** `package.json` versions are not bumped (would churn every child's manifests). Every tag carries a migration note for children in the changelog. |
| AD-007 | active | **Notification template source shape.** A registered source is `{ type, catalog, email? }` where `email = { template, templateDir?, subject(data), recipient?(data), view?(data) }`. `templateDir` absent → the notification module's own `templates` dir; `recipient` absent → `data.email` (must be a string); `view` absent → identity. Base-set types are registered through the same registry, so `EmailChannel` and the renderer resolve every type the same way and hold no per-type code. Breaking for v0.1 products that registered `{ template, templateDir, subject }` at the top level — migration note. |
| AD-008 | active | **`Mailer` is transport-only**: `send({ to, subject, html, idempotencyKey? })`. Rendering happens in `EmailChannel` (binding → recipient → subject → template → transport). Test doubles implement one method. `LogMailer` logs `to`, `subject`, `idempotencyKey` and the `href`s extracted from the HTML so dev flows keep the raw link in the log. |
| AD-009 | active | **Audit extension is one runtime registry** (`AuditRegistry`, exported by `AuditModule`): ref targets (column → `{schema, table, labelColumn}`), table owners (table → permission key), aggregate satellites and technical tables. Base-set (identity, tag) registrations move behind the same registry so consumers have one lookup path. Duplicate registration throws. Coverage lists (`AUDITED`/`EXEMPT`/`MODULE_SCHEMAS`) stay a platform-only test guard. |
| AD-010 | active | **Generic upload profiles**: `avatar`, `access-link-avatar`, `document`, `image`, `multi`. `feedback-attachment` becomes `multi` (route-uploadable, any bytes, ≤100 files, restricted); `credit-receipt`, `accommodation-type-image`, `report-artifact` are removed. Env `ATTACHMENT_FEEDBACK_MAX_FILE_BYTES/TOTAL_BYTES` → `ATTACHMENT_MULTI_MAX_FILE_BYTES/TOTAL_BYTES`; `ATTACHMENT_REPORT_MAX_BYTES` dropped. Product profiles carry static limits in the slot file. |
| AD-011 | active | **Coverage sweep verdicts are the deliverable, not the fixes.** Hits inside the five points' files are fixed in v0.2; every other `remove` / `open slot` verdict becomes a follow-up GitHub issue linked from the verdict table posted on issue #1. |
