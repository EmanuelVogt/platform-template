| AD-001 | superseded by AD-013 (v1) | **Product slot files.** Contract-facing closed sets (permission catalogs, access profiles, upload profiles) are extended through *static slot files* the platform ships empty and the product fills with additive one-liners: `shared/kernel/access/product-permission-catalogs.ts` (precedent), `shared/kernel/access/product-access-profiles.ts`, `shared/kernel/upload/product-upload-profiles.ts`. They are static because the Zod contract (`z.enum`) is evaluated at import time and must reach `openapi.json` → Kubb → web with literal types. Slot files are the only platform files a product edits, alongside the composition root (`app.module.ts`, `db/schema.ts`, `product-routes.tsx`); the platform never adds content to them after creation, so `copier update` 3-way merge stays clean. Behaviour that is only needed at boot (notification template sources, audit registrations) uses **runtime registries** the product fills from its own module (`OnModuleInit`), never a slot file. |
| AD-002 | superseded by AD-014 (v1) | **`professional` stays a base-set access profile in v0.2** (`master`, `admin`, `professional`). The identity professional slice (scope/commitments ports, directory + assignment facades, five satellite tables in baseline 0000, `areaIds/serviceIds/schedulingAreaIds` in the user contract) is far larger than the profile literal; extracting it is a v0.3-size change with its own migration story. The profile registry (AD-001) makes that extraction a deletion later. Pending user confirmation — see spec Assumptions. |
| AD-003 | superseded by AD-014 (v1) | **`attendsGuests` → `servesClients`** (column `serves_clients`). Neutral across service businesses; keeps the verb-phrase boolean style already used by the field. `isServiceProvider` rejected: `service` is product vocabulary in the coverage sweep. |
| AD-004 | superseded by AD-014 (v1) | **Access profile persistence stays a DB enum** (`identity.access_profile`); a product adds a value with `ALTER TYPE identity.access_profile ADD VALUE IF NOT EXISTS '<key>'` in its own migration. Trade-off table in design.md. Caveat documented for products: a value added inside a migration transaction cannot be used by DML in the same migration batch (Postgres ≥ 12). |
| AD-005 | superseded by AD-015 (v1) | **Platform migrations after the baseline exist.** They keep `NNNN_<module>_<slug>` numbering continuing from 0004 and a `when` chosen at authoring time.
