## Contexto

Até a `2.x`, `identity/single-tenant` carregava a fatia profissional inteira dentro do agregado
`User`: as colunas `serves_clients` e `birth_date` em `identity.users`, cinco tabelas satélite
(`user_professional_areas`, `user_professional_services`, `user_scheduling_areas`,
`user_professional_schedule_configs` — com `_slots` e `_blocks` — e `professional_default_hours`)
e o literal `professional` no enum `identity.access_profile`.

A `3.0.0` corta o agregado. A fatia vira uma entrada própria, `professional`, que declara
`professional_profile` (PK `user_id`, FK para `identity.users.id` com `ON DELETE CASCADE`) mais as
satélites, e que `dependsOn` identity — nunca o contrário. O identity para de chamar a fatia, então
o ciclo `identity ↔ professional` não se forma e nenhum token novo sobe para `shared/kernel/**`.

## Impacto

A quebra tem três frentes, todas visíveis no filho:

1. **Schema.** `identity.users` perde `serves_clients` e `birth_date`, e as cinco satélites saem do
   schema `identity`. Sem o passo 2 abaixo, o conteúdo delas se perde na primeira regeneração de
   migração — este é o único risco de perda de dado da release.
2. **Contrato.** `createUser`, `updateUser`, `listUsers`, `setPassword` e `updateMyProfile` perdem
   `areaIds`, `serviceIds` e `schedulingAreaIds`. Nenhum `operationId` some: são os mesmos
   endpoints mudando de forma, então o cliente gerado e o front quebram na compilação — não em
   runtime, e não em silêncio.
3. **Enum.** `identity.access_profile` deixa de trazer `professional` no conjunto base. Um filho
   que use o literal precisa do passo 3; um filho que queira mantê-lo pode declará-lo como perfil
   de produto e pular esse passo inteiro.

Herdado, não criado por esta mudança: `areaId`/`serviceId` das satélites continuam `text` sem FK.
A entrada nova declara essa dívida no próprio README em vez de fingir que ela não existe.

## Passos

1. **Instale a entrada nova antes de mexer no identity**: `pnpm platform module add professional`.
   O `schemaExports` do `module.json` dela é a lista canônica das seis tabelas e dos nomes com que
   elas passam a existir — use essa lista, não os nomes antigos, como alvo do passo 2.

2. **Migre os dados**, em uma migração de produto sua, antes de qualquer `drizzle-kit generate`
   que derrube as colunas:

   ```sql
   INSERT INTO professional.professional_profile
     (user_id, serves_clients, birth_date, created_at, updated_at)
   SELECT id, serves_clients, birth_date, now(), now()
     FROM identity.users
    WHERE serves_clients OR birth_date IS NOT NULL
   ON CONFLICT (user_id) DO NOTHING;

   -- uma por satélite, do nome antigo para o nome declarado no schemaExports novo
   ALTER TABLE identity.user_professional_areas SET SCHEMA professional;
   ```

3. **Derrube o literal do enum.** O PostgreSQL não tem `DROP VALUE`: o único caminho é recriar o
   tipo. Rode em uma transação **separada** da que criou qualquer literal novo (AD-004 documenta a
   armadilha simétrica: valor acrescentado por `ALTER TYPE ... ADD VALUE` não pode ser usado por
   DML na mesma transação). O bloco abaixo é idempotente — reexecutá-lo não faz nada:

   ```sql
   DO $$
   BEGIN
     IF NOT EXISTS (
       SELECT 1 FROM pg_enum e
         JOIN pg_type t ON t.oid = e.enumtypid
         JOIN pg_namespace n ON n.oid = t.typnamespace
        WHERE n.nspname = 'identity'
          AND t.typname = 'access_profile'
          AND e.enumlabel = 'professional'
     ) THEN
       RETURN;
     END IF;

     -- reatribua as linhas antes de tirar o literal do tipo
     UPDATE identity.users
        SET access_profile = 'admin'
      WHERE access_profile = 'professional';

     ALTER TYPE identity.access_profile RENAME TO access_profile__old;

     -- os literais que o SEU ACCESS_PROFILES rende sem `professional`:
     -- BASE_ACCESS_PROFILES ('master', 'admin') + os seus PRODUCT_ACCESS_PROFILES
     CREATE TYPE identity.access_profile AS ENUM ('master', 'admin');

     ALTER TABLE identity.users
       ALTER COLUMN access_profile DROP DEFAULT,
       ALTER COLUMN access_profile TYPE identity.access_profile
         USING access_profile::text::identity.access_profile,
       ALTER COLUMN access_profile SET DEFAULT 'admin';

     DROP TYPE identity.access_profile__old;
   END
   $$;
   ```

   O índice parcial de `identity.users` com predicado `access_profile = 'master'` é reconstruído
   junto pelo `ALTER COLUMN ... TYPE`. Se a sua versão de PostgreSQL recusar, derrube o índice
   antes do bloco e deixe o `drizzle-kit` recriá-lo depois.

4. Atualize a entrada do identity (`pnpm platform module update identity`, ou o skill
   `port-module-update` se a cópia local já divergiu) e regenere o contrato: os cinco schemas do
   passo 2 do Impacto mudam de forma e o cliente gerado precisa acompanhar.

5. Confirme com `pnpm test:db` e `pnpm test:e2e`, e registre a aplicação em
   `docs/advisories/APPLIED.md` — uma linha, nunca edite este arquivo.
