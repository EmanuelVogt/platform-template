# Project State — platform-template

## Decisions

Active project-level decisions. Every design must conform or supersede explicitly.

| ID | Status | Decision |
| --- | --- | --- |
| AD-001 | superseded by AD-013 (v1) | **Product slot files.** Contract-facing closed sets (permission catalogs, access profiles, upload profiles) are extended through *static slot files* the platform ships empty and the product fills with additive one-liners: `shared/kernel/access/product-permission-catalogs.ts` (precedent), `shared/kernel/access/product-access-profiles.ts`, `shared/kernel/upload/product-upload-profiles.ts`. They are static because the Zod contract (`z.enum`) is evaluated at import time and must reach `openapi.json` → Kubb → web with literal types. Slot files are the only platform files a product edits, alongside the composition root (`app.module.ts`, `db/schema.ts`, `product-routes.tsx`); the platform never adds content to them after creation, so `copier update` 3-way merge stays clean. Behaviour that is only needed at boot (notification template sources, audit registrations) uses **runtime registries** the product fills from its own module (`OnModuleInit`), never a slot file. |
| AD-002 | superseded by AD-014 (v1) | **`professional` stays a base-set access profile in v0.2** (`master`, `admin`, `professional`). The identity professional slice (scope/commitments ports, directory + assignment facades, five satellite tables in baseline 0000, `areaIds/serviceIds/schedulingAreaIds` in the user contract) is far larger than the profile literal; extracting it is a v0.3-size change with its own migration story. The profile registry (AD-001) makes that extraction a deletion later. Pending user confirmation — see spec Assumptions. |
| AD-003 | superseded by AD-014 (v1) | **`attendsGuests` → `servesClients`** (column `serves_clients`). Neutral across service businesses; keeps the verb-phrase boolean style already used by the field. `isServiceProvider` rejected: `service` is product vocabulary in the coverage sweep. |
| AD-004 | superseded by AD-014 (v1) | **Access profile persistence stays a DB enum** (`identity.access_profile`); a product adds a value with `ALTER TYPE identity.access_profile ADD VALUE IF NOT EXISTS '<key>'` in its own migration. Trade-off table in design.md. Caveat documented for products: a value added inside a migration transaction cannot be used by DML in the same migration batch (Postgres ≥ 12). |
| AD-005 | superseded by AD-015 (v1) | **Platform migrations after the baseline exist.** They keep `NNNN_<module>_<slug>` numbering continuing from 0004 and a `when` chosen at authoring time. Products are told to number their migrations from `1000_` (idx collisions are tolerated by drizzle, order = journal position) and, after `copier update`, to bump the `when` of incoming platform entries above their last applied migration when `db:check:journal` fails (a not-yet-applied entry may be re-stamped; an entry born in the past is silently skipped forever). |
| AD-006 | active (amended by AD-016) | **Version truth = git tag + `docs/dev/template-changelog.md`.** `package.json` versions are not bumped (would churn every child's manifests). Every tag carries a migration note for children in the changelog. |
| AD-007 | superseded by AD-014 (v1) | **Notification template source shape.** A registered source is `{ type, catalog, email? }` where `email = { template, templateDir?, subject(data), recipient?(data), view?(data) }`. `templateDir` absent → the notification module's own `templates` dir; `recipient` absent → `data.email` (must be a string); `view` absent → identity. Base-set types are registered through the same registry, so `EmailChannel` and the renderer resolve every type the same way and hold no per-type code. Breaking for v0.1 products that registered `{ template, templateDir, subject }` at the top level — migration note. |
| AD-008 | superseded by AD-014 (v1) | **`Mailer` is transport-only**: `send({ to, subject, html, idempotencyKey? })`. Rendering happens in `EmailChannel` (binding → recipient → subject → template → transport). Test doubles implement one method. `LogMailer` logs `to`, `subject`, `idempotencyKey` and the `href`s extracted from the HTML so dev flows keep the raw link in the log. |
| AD-009 | superseded by AD-014 (v1) | **Audit extension is one runtime registry** (`AuditRegistry`, exported by `AuditModule`): ref targets (column → `{schema, table, labelColumn}`), table owners (table → permission key), aggregate satellites and technical tables. Base-set (identity, tag) registrations move behind the same registry so consumers have one lookup path. Duplicate registration throws. Coverage lists (`AUDITED`/`EXEMPT`/`MODULE_SCHEMAS`) stay a platform-only test guard. |
| AD-010 | superseded by AD-014 (v1) | **Generic upload profiles**: `avatar`, `access-link-avatar`, `document`, `image`, `multi`. `feedback-attachment` becomes `multi` (route-uploadable, any bytes, ≤100 files, restricted); `credit-receipt`, `accommodation-type-image`, `report-artifact` are removed. Env `ATTACHMENT_FEEDBACK_MAX_FILE_BYTES/TOTAL_BYTES` → `ATTACHMENT_MULTI_MAX_FILE_BYTES/TOTAL_BYTES`; `ATTACHMENT_REPORT_MAX_BYTES` dropped. Product profiles carry static limits in the slot file. |
| AD-011 | superseded by AD-013 (v1) | **Coverage sweep verdicts are the deliverable, not the fixes.** Hits inside the five points' files are fixed in v0.2; every other `remove` / `open slot` verdict becomes a follow-up GitHub issue linked from the verdict table posted on issue #1. |
| AD-012 | active | **Pre-push coverage bar is 95% S/B/F/L** on api unit (`jest --coverage`, `coverageProvider: "v8"`, `@swc/jest`) and web (`vitest --coverage`, v8). Combined `test:cov:all` nyc floors stay independent and are not this bar. Future features must not lower the pre-push thresholds. |
| AD-013 | active (v1, 2026-08-21) | **Catalog model — supersedes AD-001, AD-011.** The template ships the kernel only; former base-set modules are entries in `catalog/` (in this repo, `copier.yml` `_exclude`), copied into and owned by the child via `pnpm platform module add <name> [--variant]`, recorded in `.platform-modules.lock`. Slot files and the base-set notion are retired; `module-boundaries.spec.ts` gains RULE C (no module vocabulary in `shared/**`, web `app/**`/`shared/**`). One entry per module, variant = sub-entry, no bundles (`dependsOn` composes). Sweep follow-ups #2–#8 are absorbed by entries (`module.json.absorbs`). |
| AD-014 | active (v1, 2026-08-21) | **Module internals are entry-local decisions — supersedes AD-002, AD-003, AD-004, AD-007, AD-008, AD-009, AD-010.** Profiles/professional slice, column names, DB enum policy, notification source shape, mailer, audit registry, upload profiles live in the entry README § Decisões and CHANGELOG; STATE.md governs kernel + tooling only. |
| AD-015 | active (v1, 2026-08-21) | **Migrations — supersedes AD-005.** Template journal = `0000_kernel_baseline` + `0001_kernel_outbox_notify`, kernel numbering `NNNN_kernel_<slug>`. Entries ship tables as TS + `migrations/custom/*.sql`; `module add` generates the migration in the child with `drizzle-kit generate` (+ `--custom` for shipped SQL), so numbering, `when` and the snapshot chain are the child's. Products keep `1000_`. Existing v0.2 children are never rewritten (`module adopt`). |
| AD-016 | active (v1, 2026-08-21) | **Entry versions — amends AD-006.** `module.json.version` + CHANGELOG heading + tag `catalog/<name>[-<variant>]@x.y.z` are the truth for an entry; advisories `affects` target entry versions. Template tag + `docs/dev/template-changelog.md` remain the kernel truth; `package.json` still not bumped. |
| AD-017 | active (v1, 2026-08-21) | **Kernel access seam.** Kernel ships `@RequirePermission`/`@Public`/`@Authenticated` metadata and a global `AccessGuard` that delegates to an `ACCESS_POLICY` port; no provider → 403 `access-policy-missing` on non-public routes (fail closed; default requirement = authenticated). ALS holds an opaque `Actor { id, kind, tenantId? }` + symbol-keyed `extensions`; identity sets the actor from middleware and implements the policy. `tenantId` is the only multi-tenant seam. |

UI/router wiring ships as README recipes. Generated client never shipped; `module add` runs `pnpm contract`. |
| AD-019 | active (v1, 2026-08-21) | **Advisories channel.** `docs/advisories/ADV-YYYYMMDD-NN.md` (frontmatter `id, kind, module, affects, severity, detect, fix, parity`), immutable, reach children via copier; child keeps `docs/advisories/APPLIED.md` (`_skip_if_exists`); `.claude/hooks/pending-advisories.mjs` injects `advisories − ledger` filtered by lock versions. | AD-020 | active (v1, 2026-08-21) | **Generated registries.** `apps/api/src/platform-modules.ts` (`PLATFORM_MODULES`) and `apps/api/src/db/platform-schema.ts` are generated from the lock by `module add/adopt/--rollback`; `app.module.ts` and `db/schema.ts` spread/re-export them. No markers, no hand edits; web has no registry (raw web). |
| AD-021 | active (v1, 2026-08-21) | **Entry-to-entry coupling goes through ports — extends AD-013/AD-017.** An entry must install alone in a kernel-only child. Where one entry needs another's behaviour, the consumer declares a **port** and the provider binds it (the `ACCESS_POLICY` pattern), so `dependsOn` stays acyclic and a missing provider degrades that feature instead of failing module resolution. Discovered in v1 wave 3: `identity` imported `AttachmentModule` unconditionally and injected `AttachmentFacade` in three use cases (`upload-avatar`, `upload-access-link-avatar`, `set-password`), while `attachment` injects identity's `UserDirectoryFacade` — a real `identity ↔ attachment` cycle that `resolveDeps` topo-sorts over. Resolution: identity declares a file-storage port; attachment provides it. Bundles/joint install rejected (AD-013 forbids bundles); tolerating cycles in `resolveDeps` rejected (defeats install ordering). |
| AD-022 | active (v1, 2026-08-21) | **Maintenance jobs are a runtime registry, not a closed kernel union — extends AD-020.** `MAINTENANCE_SCHEDULE` is a hardcoded `const` at `apps/api/src/shared/kernel/scheduling/maintenance-schedule.ts:23-28` (`{ "outbox.purge": {cron,lockId:1}, "idempotency.purge": {cron,lockId:2} } as const satisfies Record<string, MaintenanceJobSpec>`; `MaintenanceJobSpec = { cron: string; lockId: number; atomic?: boolean; timeZone?: string }`), and `@MaintenanceJob(name)` (`maintenance-job.decorator.ts:5,22`) only accepts a name already present as a key — so **no catalog entry can register a maintenance job without editing a kernel file**, and identity's real jobs `auth-events.purge` / `email-change.revert` are dead code in every child (an earlier draft named `purge-users`, which is an admin route, not a job — corrected in wave 4b.2). Resolution: the kernel ships a `MaintenanceRegistry` (same shape as AD-009's `AuditRegistry`); entries register at boot; duplicate name and colliding `lockId` both throw; the kernel's own two jobs register through the same path. Readers to migrate: `maintenance-runtime.ts:14,135,174`, `maintenance-job.decorator.ts:5,22`, `maintenance-schedule.spec.ts:8,17,30,141,145,150`, `maintenance-runtime.int-spec.ts:20,116`. The spec at `maintenance-schedule.spec.ts:138-146` ("varredura resolve exatamente um arquivo de corpo por job do registro") asserts one body file per registered job — it must become registry-driven or be scoped to kernel jobs only. Discovered in v1 wave 4 (T22 cutover); implemented by T22d. |
| AD-023 | planned (test-suite-refactor) | **Test harness layering.** Runner plumbing (jest configs, containers, env) lives in `apps/api/test/`; everything a spec imports lives in `apps/api/src/shared/test/{unit,int,e2e,parity}` with kernel vocabulary only; each catalog entry ships `api/testing/` (seed, login, fakes, fixtures) listed in `module.json.files`, importable by dependents only through `dependsOn`. Constrains v1 entry anatomy (README § Tests) and `docs/test/testing.md`. |
| AD-024 | active (v1, 2026-08-21) | **Entry-to-entry port tokens live in the kernel — closes a hole in AD-021.** AD-021 says the consumer declares a port and the provider binds it, but a token declared inside the consumer entry cannot be bound without the provider importing that entry — the violation AD-021 exists to prevent, in the reverse direction. Wave 4b.2 hit it head on: identity declared `AUDIT_TRAIL_PURGER` in `catalog/identity/single-tenant/api/domain/ports/audit-trail-purger.ts` and the audit entry could not bind it. The `ACCESS_POLICY` precedent works only because its token lives in the kernel. Resolution: the **token and interface** of every entry-to-entry port live in the kernel, in module-agnostic vocabulary (RULE C still applies), beside the concept they belong to (`shared/kernel/<concept>/<name>.port.ts`, the `access/access-policy.port.ts` shape) — **not** in a separate `ports/` tree, which T22i found would be a second lookup path for the same kind of thing (AD-009). Landed at `shared/kernel/audit-trail/audit-trail-purger.port.ts` and `shared/kernel/profile-image/profile-image-store.port.ts`; the consumer injects with `@Optional()`, the provider binds, neither imports the other. Applies to `AUDIT_TRAIL_PURGER`/`AuditTrailPurger` and to T17c's `PROFILE_IMAGE_STORE`/`ProfileImageStore`. Implemented by T22i. |
| AD-025 | active (v1, 2026-08-21) | **Port inversion is required only where a cycle exists; elsewhere `dependsOn` carries the edge — narrows AD-021.** AD-021 reads as "an entry must install alone in a kernel-only child", which taken literally would forbid every entry-to-entry edge. Wave 4c.2 measured the real graph and that reading is unaffordable and wrong: 18 production-source cross-entry imports remain (`identity → notification` ×10 `NotificationRequested`; `audit → identity` ×7 incl. `audit.module.ts:3` importing `IdentityModule`; `attachment → identity` ×1 `UserDirectoryFacade`), and **the production graph is acyclic** — topological order `notification, identity, audit, attachment, tag`. Inverting all 18 would require kernel ports for `UserDirectoryFacade`, `PermissionCatalog` and `NotificationRequested`, i.e. pushing module vocabulary into the kernel, exactly what RULE C forbids. `dependsOn` is already a DAG that `resolveDeps` topo-sorts, and `attachment`/`audit` already declare `identity`. Resolution: **invert only edges that close a cycle**; declare the rest honestly in `dependsOn`. The one cycle today is `identity ↔ notification`, closed solely by 6 test-only imports of identity's `RATE_LIMITER` from notification's and tag's e2e — those are what must be inverted (T22m). AD-021's port mechanism is unchanged for cycles; only its "install alone" absolutism is narrowed. |
| AD-026 | active (v1, 2026-08-21) | **A cross-entry e2e lives in the entry downstream in the `dependsOn` DAG — in the dependent, never in the dependency.** Corollary of AD-025, found by T22m. Four of notification's e2e (`notifications-{email,feed,inapp,sse}`) drove identity routes — `/v1/admin/users`, `/v1/auth/login`, `/v1/auth/change-password` — needing a real argon2 hash and a session cookie. Keeping them in notification would have forced `notification → identity`, closing the `identity ↔ notification` cycle; seeding around it was impossible (the recipient columns carry no FK, but the specs need a *logged-in* user, not a row). They moved verbatim into `catalog/identity/single-tenant/api/__e2e__/`, where the dependency already points the right way. `notifications-product-extension` stayed put: it seeds `recipientId: ulid()` and issues no HTTP request, so its `RATE_LIMITER` override was provably dead weight. Discovery is unaffected — `apps/api/test/jest-e2e.json:5` `testRegex: ".*\\.e2e-spec\\.ts$"` is entry-agnostic and only ever sees an installed child. |
| AD-027 | planned (web-stack-next, 2026-08-23) | **Selectable web shell via copier path templating + symlinks.** `copier.yml` question `web_stack` (`vite` default, `next`). Both shells are real workspace members — `apps/web-vite` (package `web`, the former `apps/web`) and `apps/web-next` (package `web-next`) — excluded from the render; two root-level Jinja-named directories `{% if web_stack == '<stack>' %}apps{% endif %}/web` are symlinks to them, so exactly one renders to `apps/web`; a `_tasks` step renames `web-next` → `web` on `copy` for `next`. Rejected: Jinja-named dirs inside `apps/` (turbo expands `{…}` as a glob and registers `apps/web` twice); templated `_exclude` (matches destination paths, so it cannot keep one shell and drop the other at the same `apps/web`); `_tasks mv` of `apps/web-next` (breaks `copier update` — patches would target the old path). Probed on copier 9.17.1: Vite child byte-identical, `copier update --defaults`/`--skip-answered` touch only the answers file, Next child updates patch `apps/web` in place. Same platform contract in both shells (transport, Zod env, RFC 7807 helper, auth store, `RouteAccess` vocabulary — Next: `ROUTE_ACCESS` table + `AccessGuard` slot in `src/_app/layout`, product slot `product-shell.tsx`); FSD in Next uses `src/_app`/`src/_pages`, `app/**` = pure re-exports. Catalog entries untouched (AD-018). |
