## Contexto

A entrada `audit` migrou suas specs de Jest para Vitest (`module.json.version` `1.0.0` →
`2.0.0`). O codemod `scripts/platform/jest-to-vitest.mjs` reescreve `jest.fn|spyOn|mock|mocked|
restoreAllMocks|resetAllMocks|clearAllMocks|useFakeTimers|useRealTimers|advanceTimersByTime|
setSystemTime` para `vi.<mesmo>`, `jest.requireActual(x)` para `await vi.importActual(x)` dentro
de uma factory `async`, `jest.setTimeout(n)` para `vi.setConfig({ testTimeout: n })`, os tipos
`jest.Mock`/`jest.Mocked`/`jest.MockedFunction`/`jest.SpyInstance` para `Mock`/`Mocked`/
`MockedFunction`/`MockInstance` importados de `"vitest"`, e adiciona o `import { … } from
"vitest"` que cobre exatamente os globais usados em cada arquivo. `dependsOn` identity sobe de
`>=1.0.0 <2.0.0` para `>=2.0.0 <3.0.0`.

## Impacto

Um filho em `>=1.0.0 <2.0.0` que ainda referencia `jest.*` em `apps/api/src/modules/audit/**`
(código copiado da entrada) fica com specs que não rodam mais sob o runner Vitest do template —
`pnpm vitest run --project api apps/api/src/modules/audit` falha até a migração ser aplicada.

## Correção adicional: `schemaExports` causava `CREATE TABLE` duplicado

`module.json.schemaExports` listava `tables/audit-entry.table`, arquivo que combinava a
declaração `pgSchema("audit")` com a definição da tabela `auditEntries` — cuja tabela real é
criada pela migration manual `01_audit_trail_capture.sql` (trigger append-only, comentário
explícito no arquivo: "não é gerada pelo drizzle-kit, é criada aqui"). Com o export do arquivo
combinado, a baseline do drizzle-kit também emitia `CREATE TABLE "audit"."entries"`, que colidia
(`42P07`, relation já existe) com o `CREATE TABLE` da migration manual que roda depois — nem
`pnpm catalog:check` nem `module add audit` chegavam a completar num banco novo (o gate de DB
tier por entrada, AC3, é quem primeiro exercitou esse caminho). A correção segue o padrão de
notification/identity/attachment: a declaração `pgSchema("audit")` sai para
`tables/audit.schema.ts`, e `schemaExports` passa a listar só esse arquivo — a baseline volta a
emitir `CREATE SCHEMA "audit"` sem tentar criar a tabela. Efeito colateral: com o arquivo
combinado saindo de `schemaExports`, o guard do kernel `schema-completeness.spec.ts` (todo
`*.table.ts` em disco precisa estar no agregador do drizzle-kit, salvo allowlist) passou a
reprovar o arquivo — de propósito fora do agregador. Renomeado para
`tables/audit-entry.readmodel.ts`, fora do glob `*.table.ts`, sem precisar tocar o teste do
kernel.

## Correção adicional: specs assumindo o módulo `tag` sempre instalado

`audit-trigger.int-spec.ts`, `drizzle-ref-label.reader.int-spec.ts` e `audit.e2e-spec.ts` usavam
`tag.tags`/`truncateTag`/`POST /v1/admin/tags` como veículo de teste do mecanismo genérico de
trigger — `audit` não depende de `tag` (`module.json.dependsOn` só lista `identity`; as duas são
siblings), então um `catalog:check audit` standalone nunca cria o schema `tag`. Veículo trocado
para `identity.permission_templates` / `POST /v1/admin/permission-templates` (dependência real
declarada). `audit-coverage.int-spec.ts` passa a checar "toda tabela AUDITED tem o trigger" só
para tabelas cujo módulo está de fato instalado — `tag.tags` continua declarado em `AUDITED`
(`audit-coverage.ts`) para quando o produto final tiver as duas entradas juntas (a entrada `tag`
deve se auto-registrar em `AuditRegistry.registerTables` no próprio `OnModuleInit`, mesmo padrão
provado por `audit-product-extension.e2e-spec.ts`).

## Correção adicional: `IdentityModule` importado cru quebrava todo e2e do child

`audit.module.ts` importava a classe `IdentityModule` crua para alcançar `UserDirectoryFacade`
(nome do ator na trilha). `IdentityModule` é um módulo dinâmico (`forRoot`, `global: true`
justamente para que importar a classe crua em outro lugar não crie uma segunda instância) — mas
`audit.module.ts` importava a classe mesmo assim, criando essa segunda instância vazia; o
`configure()` dela tentava montar `AuthMiddleware` sem `SessionRepository` disponível, e QUALQUER
e2e do child (não só de audit) quebrava com "Nest can't resolve dependencies of the
AuthMiddleware... SessionRepository" assim que audit entrava no grafo — a mesma armadilha já
documentada no comentário de `attachment.module.ts`. Import removido; `UserDirectoryFacade` já
chega pelo export global do `IdentityModule.forRoot()` montado na raiz.

## Correção adicional: tabelas do identity nunca ficam auditadas sozinhas

`identity/migrations/custom/02_audit_attach.sql` documenta ela mesma a limitação: roda antes de
`audit.attach` existir sempre que `audit` é instalado depois de `identity` (a única ordem
possível, dado `dependsOn`), então sai sem anexar nada, e orienta reaplicar o passo (idempotente)
depois de instalar `audit`. Nenhum passo de `module add`/`catalog:check` faz essa reaplicação
automaticamente — os testes de audit que dependem do trigger em tabelas do identity
(`audit-trigger.int-spec.ts`, `audit-coverage.int-spec.ts`, `audit.e2e-spec.ts`) simulam esse
passo manual via `api/testing/reattach-identity-tables.ts` (novo, dentro da entrada), desfeito no
`afterAll` de cada um por `detachIdentityTables` — o trigger `audit_row` é DDL permanente que não
some com o fim do teste, e o worker de `test:db` compartilha o banco entre arquivos; sem desfazer,
a latência extra do trigger em tabelas do identity vazava para e2e do identity sem relação nenhuma
com auditoria, derrubando timeouts. Produtos reais precisam do mesmo passo manual (sem o desfazer,
claro) ao instalar `audit` sobre um `identity` já em produção — a limitação é pré-existente e
documentada na própria migration do identity, não nova desta migração. Produtos em `1.x` que já rodaram
`module add audit` contra um banco real: se `db:generate` já tiver produzido uma migração
duplicada de `audit.entries` a partir do export antigo, ela é histórico imutável — o efeito da
correção é não repetir o conflito em `db:generate` futuros, não reescrever migrações já geradas.

## Passos

1. Rode `node scripts/platform/jest-to-vitest.mjs apps/api/src/modules/audit` no filho.
2. Confirme com `rg -l 'jest\.' apps/api/src/modules/audit` (sem saída).
3. Rode `pnpm vitest run --project api apps/api/src/modules/audit` e confira que a suíte passa.
4. Registre a aplicação em `docs/advisories/APPLIED.md` (uma linha, nunca edite este arquivo).
