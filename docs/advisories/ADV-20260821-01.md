## Contexto

A entrada `attachment` migrou suas specs de Jest para Vitest (`module.json.version` `1.0.0` →
`2.0.0`). O codemod `scripts/platform/jest-to-vitest.mjs` reescreve `jest.fn|spyOn|mock|mocked|
restoreAllMocks|resetAllMocks|clearAllMocks|useFakeTimers|useRealTimers|advanceTimersByTime|
setSystemTime` para `vi.<mesmo>`, `jest.requireActual(x)` para `await vi.importActual(x)` dentro
de uma factory `async`, `jest.setTimeout(n)` para `vi.setConfig({ testTimeout: n })`, os tipos
`jest.Mock`/`jest.Mocked`/`jest.MockedFunction`/`jest.SpyInstance` para `Mock`/`Mocked`/
`MockedFunction`/`MockInstance` importados de `"vitest"`, e adiciona o `import { … } from
"vitest"` que cobre exatamente os globais usados em cada arquivo. `dependsOn` identity sobe de
`>=1.0.0 <2.0.0` para `>=2.0.0 <3.0.0`.

## Impacto

Um filho em `>=1.0.0 <2.0.0` que ainda referencia `jest.*` em
`apps/api/src/modules/attachment/**` (código copiado da entrada) fica com specs que não rodam
mais sob o runner Vitest do template — `pnpm vitest run --project api
apps/api/src/modules/attachment` falha até a migração ser aplicada.

## Correção adicional: `CREATE SCHEMA` ausente

Junto com a migração para Vitest, `module.json.schemaExports` passou a listar
`tables/attachment.schema` (a declaração `pgSchema("attachment")`), que faltava desde a `1.0.0`.
Sem ela, o snapshot do `drizzle-kit` não registrava o schema lógico e a migração baseline gerada
para um filho não emitia `CREATE SCHEMA "attachment"`, falhando com `3F000` (schema inexistente)
ao aplicar as tabelas em um banco novo. Produtos em `1.x` que já geraram migrações a partir desta
entrada devem rodar manualmente `CREATE SCHEMA IF NOT EXISTS "attachment";` antes de aplicar
novas migrações geradas a partir da `2.0.0`; quem estiver adotando a entrada pela primeira vez a
partir da `2.0.0` não precisa de nenhum passo manual.

## Correção adicional: migração "0005" ausente da entrada

`drizzle-attachment.repository.int-spec.ts` (linha de regressão de dados) referenciava
`apps/api/drizzle/migrations/0005_attachment_generic_upload_profiles.sql`, arquivo do kernel
pré-catálogo removido em `e30648f` e nunca recriado dentro de `catalog/attachment/**` — o teste
nunca rodou de fato num child (mesma causa-raiz da ausência de `CREATE SCHEMA`: o `catalog:check`
nunca exercia a DB tier). A migração volta como `migrations/custom/01_generic_upload_profiles.sql`
(listada em `module.json.customMigrations`); o teste passa a localizar o arquivo gerado pelo
sufixo do nome, já que a numeração de customMigrations é sequencial pela ordem de install do
child, não fixa.

## Correção adicional: `dependsOn` sem `notification`

O e2e cruzado relocado (seção acima) sobrepõe a porta `MAILER` de `notification` para
interceptar o e-mail de convite e extrair o token do access-link — o fluxo de convite de
`identity`, exercitado end-to-end a partir de `attachment`, publica pela porta real de
`notification`. É um acoplamento de produção genuíno, não incidental, e o guard
`scripts/platform/__tests__/catalog-custom-migrations.test.mjs` ("dependsOn de cada entrada real
do catálogo é derivado dos imports que cruzam para outra entrada") cobra a declaração honesta:
`module.json.dependsOn` ganha `{ "name": "notification", "range": ">=2.0.0 <3.0.0" }`, a mesma
faixa que `identity` já declara para `notification`. `notification.dependsOn` é `[]`, então o
grafo de produção segue acíclico (`notification` → nada; `identity` → `notification`; `attachment`
→ `identity`, `notification`) — não é um fechamento de ciclo, então nenhuma inversão de porta é
necessária (AD-025).

## Passos

1. Rode `node scripts/platform/jest-to-vitest.mjs apps/api/src/modules/attachment` no filho.
2. Confirme com `rg -l 'jest\.' apps/api/src/modules/attachment` (sem saída).
3. Rode `pnpm vitest run --project api apps/api/src/modules/attachment` e confira que a suíte
   passa.
4. Registre a aplicação em `docs/advisories/APPLIED.md` (uma linha, nunca edite este arquivo).
