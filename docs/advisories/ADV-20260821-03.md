## Contexto

A entrada `identity/single-tenant` migrou suas specs de Jest para Vitest (`module.json.version`
`1.0.0` → `2.0.0`). O codemod `scripts/platform/jest-to-vitest.mjs` reescreve `jest.fn|spyOn|
mock|mocked|restoreAllMocks|resetAllMocks|clearAllMocks|useFakeTimers|useRealTimers|
advanceTimersByTime|setSystemTime` para `vi.<mesmo>`, `jest.requireActual(x)` para
`await vi.importActual(x)` dentro de uma factory `async`, `jest.setTimeout(n)` para
`vi.setConfig({ testTimeout: n })`, os tipos `jest.Mock`/`jest.Mocked`/`jest.MockedFunction`/
`jest.SpyInstance` para `Mock`/`Mocked`/`MockedFunction`/`MockInstance` importados de `"vitest"`,
e adiciona o `import { … } from "vitest"` que cobre exatamente os globais usados em cada arquivo.
`dependsOn` notification sobe de `>=1.0.0 <2.0.0` para `>=2.0.0 <3.0.0`.

## Impacto

Um filho em `>=1.0.0 <2.0.0` que ainda referencia `jest.*` em `apps/api/src/modules/identity/**`
ou `apps/web/src/entities/identity/**` (código copiado da entrada) fica com specs que não rodam
mais sob o runner Vitest do template — `pnpm vitest run --project api
apps/api/src/modules/identity` e `pnpm vitest run --project web apps/web/src/entities/identity`
falham até a migração ser aplicada.

## Correção adicional: `CREATE SCHEMA` ausente

Junto com a migração para Vitest, `module.json.schemaExports` passou a listar
`tables/identity.schema` (a declaração `pgSchema("identity")`), que faltava desde a `1.0.0`. Sem
ela, o snapshot do `drizzle-kit` não registrava o schema lógico e a migração baseline gerada para
um filho não emitia `CREATE SCHEMA "identity"`, falhando com `3F000` (schema inexistente) ao
aplicar as tabelas em um banco novo. Produtos em `1.x` que já geraram migrações a partir desta
entrada devem rodar manualmente `CREATE SCHEMA IF NOT EXISTS "identity";` antes de aplicar novas
migrações geradas a partir da `2.0.0`; quem estiver adotando a entrada pela primeira vez a partir
da `2.0.0` não precisa de nenhum passo manual.

## Correção adicional: ordem de `listByServiceIds` não determinística num INSERT em lote

`user_professional_services.created_at` usava `defaultNow()` (`now()`), que no Postgres é a hora
de INÍCIO DA TRANSAÇÃO — constante para todas as instruções dela, não por linha. O gate de DB tier
por entrada (`catalog:check attachment`, que instala `identity` como dependência) expôs que
`DrizzleProfessionalAssignmentRepository.replaceForService` insere vários vínculos num único
`INSERT ... VALUES (...), (...)`: todas as linhas desse lote empatam em `created_at`, e o
`ORDER BY created_at, user_id` de `listByServiceIds` passa a desempatar por `user_id` (ULID,
sem relação com a ordem de inserção) — o teste
"replaceForService > insere vínculos novos com isDefault e auto-atribui a área ausente" (que
assevera a ordem dos vínculos, mesmo contrato do teste irmão "agrupa vínculos por serviço com
isDefault, na ordem do vínculo") passava por acaso quando a entrada rodava isolada e falhava de
forma reprodutível dentro do filho de `attachment`, dependendo de qual ULID sorteia menor. A
coluna passa a usar `clock_timestamp()` (hora real, avaliada por linha, não por transação) como
default — cada linha do mesmo `INSERT` em lote recebe um instante distinto, preservando a ordem de
inserção sem exigir uma coluna nova. Nenhuma asserção de teste foi alterada.

## Correção adicional: Passo manual para `clock_timestamp()` na `user_professional_services`

Produtos em `1.x` que já geraram migrações a partir desta entrada devem rodar manualmente
`ALTER COLUMN created_at SET DEFAULT clock_timestamp();` na tabela `user_professional_services`
antes de aplicar novas migrações geradas a partir da `2.0.0`; quem estiver adotando a entrada pela
primeira vez a partir da `2.0.0` não precisa de nenhum passo manual.

## Passos

1. Se o produto estiver em `1.x`, rode manualmente `ALTER COLUMN created_at SET DEFAULT clock_timestamp();` na tabela `user_professional_services`.
2. Rode `node scripts/platform/jest-to-vitest.mjs apps/api/src/modules/identity
   apps/web/src/entities/identity` no filho.
3. Confirme com `rg -l 'jest\.' apps/api/src/modules/identity apps/web/src/entities/identity`
   (sem saída).
4. Rode `pnpm vitest run --project api apps/api/src/modules/identity` e `pnpm vitest run
   --project web apps/web/src/entities/identity` e confira que as suítes passam.
5. Registre a aplicação em `docs/advisories/APPLIED.md` (uma linha, nunca edite este arquivo).
